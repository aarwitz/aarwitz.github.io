Why You Can't Do Motor Control on Linux (And Why That's Fine)

Understanding the MCU + MPU split in robotics

December 24, 2025

I was aware of the limitations of Linux for motor control, but I thought for soft real-time tasks like reading motor encoders and running PID loops at a few kHz, it would be "good enough" with the right tweaks. If you've tried to build a robot with a Jetson or Raspberry Pi, you've probably discovered a frustrating truth: reading motor encoders from Linux is terrible. Pulses get missed, velocity estimates jitter, and control loops feel sloppy. You might wonder if you're doing something wrong.

You're not. Linux just isn't built for this. Here's why—and what to do about it.

The Problem: Hard Real-Time vs. Best-Effort

Motor encoders produce asynchronous pulse trains. Every edge matters. Miss one, and your position estimate drifts. To calculate velocity, you need to count pulses over a precise, known time window. If that window stretches or shrinks unpredictably, your velocity estimate becomes garbage.

This is a hard real-time problem. "Hard real-time" means: if you miss a deadline, the system fails. Not "fails gracefully"—fails.

Linux is not a hard real-time system. It's a general-purpose operating system optimized for throughput, fairness, and safety. When you read a GPIO pin or talk to hardware from Linux userspace, every operation is a syscall—a request that crosses the user-kernel boundary, gets queued by the scheduler, and executes whenever the kernel decides it's safe.

That delay is unbounded. The scheduler might preempt you. A page fault might trigger. An interrupt handler might run. You have no guarantees.

Can't You Just Use PREEMPT_RT?

You can get closer to real-time behavior with the right setup. With PREEMPT_RT patches, isolated CPU cores, IRQ affinity tuning, and carefully pinned RT threads, Linux can achieve soft real-time performance:

  • Wake a thread within 10–50 µs worst-case
  • Run control loops at 1–5 kHz
  • Avoid priority inversion
  • Behave predictably under load

This is real, and it's used in industrial automation, CNC machines, and other systems where "mostly on time" is good enough.

But here's what's missing:

  • No guarantees about GPIO edge timing
  • No guarantees about I²C transaction completion
  • No deterministic response to asynchronous external events

PREEMPT_RT improves thread scheduling. It doesn't give you hardware-level determinism. It doesn't turn Linux into a microcontroller. For encoder decoding, you still have jitter. You will still miss edges.

Why SMBus Doesn't Help

Some motor drivers expose control over SMBus or I²C. You might think: "Great, I'll just poll the encoder count over I²C." This fails for the same reason.

SMBus from Linux userspace is designed for slow configuration and telemetry—reading temperatures, setting fan speeds, querying battery status. It deliberately adds timeouts, transaction framing, and safety checks to prevent any single process from wedging the bus.

This is good design for a general-purpose OS. But it makes SMBus unsuitable for control loops. The bus is too slow, transactions are too unpredictable, and the kernel will abort your transfer if you try to hog it.

Why Arduino "Works" (Sort Of)

An Arduino has no operating system. No scheduler. No syscalls. Just your code running in a loop. Interrupts fire immediately with bounded latency. This is why Arduino can do encoder decoding: you attach interrupt handlers to GPIO pins, and they fire on every edge.

But this approach has limits:

  • Every encoder pulse triggers an interrupt
  • CPU load scales with motor speed
  • At high RPM, interrupt handlers start overlapping
  • Jitter increases, pulses get missed

Arduino works fine for hobby robots with slow motors and low-resolution encoders. But it doesn't scale.

The Real Solution: Hardware Encoder Support

High-end microcontrollers—like STM32, NXP i.MX RT, and TI C2000—have something Arduino lacks: hardware quadrature decoder logic built into the timer peripherals.

This is not software. This is not firmware. This is actual digital logic—gates and flip-flops—running continuously in silicon, independent of the CPU.

Here's what the hardware does:

  • Watches encoder A and B channels
  • Implements a state machine to determine rotation direction
  • Automatically increments or decrements a counter
  • Handles x1, x2, or x4 edge multiplication
  • Filters glitches

All of this happens with zero CPU involvement. No interrupts. No polling. The CPU just reads a counter register whenever it needs the current position.

Why Bit Width Matters

Arduino's 8-bit timers overflow constantly. Even 16-bit counters wrap quickly at high speeds. Handling overflow adds complexity and failure modes.

STM32 offers 32-bit timers. A 32-bit counter at 1 MHz takes 71 minutes to overflow. You can safely ignore wraparound. Your math gets simpler. Your code gets safer.

What About Kernel Drivers?

You might think: "Why not write a Linux kernel driver that handles encoders?" Some people do this. It's a bad idea.

Kernel space has lower latency than userspace, but it's still not deterministic. You're still at the mercy of the scheduler, interrupt handlers, and CPU cache. And now you've coupled your motor control logic to the kernel, making it harder to maintain, debug, and port.

A $5 STM32 solves the problem better than a kernel driver. Use it.

The Correct Architecture

Industry-standard robotics systems use a two-layer architecture: 

Encoders + Motors → MCU (hardware decode + PID)
                         ↓
                  position, velocity, state
                         ↓
               Linux / Jetson (ROS, planning, vision)

The microcontroller handles:

  • Encoder decoding (in hardware)
  • PID control loops (at fixed rate)
  • Motor PWM generation
  • Safety interlocks

The Linux system handles:

  • Path planning
  • Computer vision
  • High-level logic
  • User interfaces

Communication between the two happens over a simple serial protocol (UART, CAN, etc.) at a reasonable rate—maybe 50-100 Hz. The MCU sends position and velocity. The Linux system sends target velocities or trajectory points.

Why This Division Makes Sense

Linux deliberately trades timing determinism for safety, isolation, and flexibility. That's the right trade-off for a general-purpose OS. You want the kernel to protect hardware from rogue processes. You want the scheduler to keep the system responsive.

A microcontroller is the opposite: it's a timing authority with bounded latency and hardware assistance. It does one thing well.

Use each for what it's good at. Don't fight the OS. Don't try to turn Linux into a real-time system. Add a $5 chip and move on.

Summary

Real-time encoder decoding requires deterministic timing and hardware assistance. Microcontrollers provide this via dedicated timer logic. Linux deliberately trades timing determinism for safety and isolation. The MCU + MPU split is not a compromise—it's the correct and industry-standard design. Each layer does what it's built to do, and the system works better as a result.
